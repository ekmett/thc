# Whole-program extraction and library/runtime boundary

Research date: 2026-09-22. This historical architecture/source audit preceded the implementation. No compiler, plugin, foundation package, or Eta executable was built or run as part of this audit. Exact inspected revisions and the selected-file inventory are retained in [the provenance manifest](whole-program-provenance.json); downloaded source snapshots were local research scratch files. Cadenza was not modified. See the [README](../README.md) and [Map report](../docs/map-example.md) for the current implementation and its pinned GHC 9.14.1 toolchain.

## Recommendation

The main architecture decision is to use **optimized pre-Tidy Core as the authoritative input**, paired with optimized STG for reference and importer comparisons. Use an exactly pinned GHC 9.10.3 exporter adapter and an explicit structured metadata sidecar. This tooling audit independently finds STG the simpler bootstrap because the existing exporter and downstream tooling already consume it; that is an implementation-risk inference, not a decision to discard Core or override the main design. STG remains a credible fallback if the Core lowering does not demonstrate a benefit. A standard `.hi` alone is not a whole-program input. Neither GHC's native libraries nor its RTS can simply become JVM code by linking them to a Truffle interpreter.

The strongest positive finding is that the current WPC source already exports `module.fullcore-hi` as well as `module.stgbin`. The strongest qualification is that boot-library production, complete symbol closure, and the new runtime's compatibility layer remain substantial work. WPC is useful infrastructure, not evidence that these problems have been solved for THC.

## What the exporter actually captures

`WPC.Plugin` appends a Core pass capturing `ModGuts`, installs driver/phase/link/foreign-desugaring hooks, and captures `[CgStgTopBinding]` through `stgToCmmHook` while continuing GHC's ordinary native code generation. This is code-generation STG, not a fresh high-level Haskell AST. Plugin ordering matters: another plugin inserted afterward can change what corresponds to final emitted code. For THC, capture points and ordering must be explicit; GHC also provides a late plugin receiving fully optimized `CgGuts`. [Plugin source](https://github.com/grin-compiler/ghc-whole-program-compiler-project/blob/a99ba59f7286a46aed19e9faba3acc6833b21920/wpc-plugin/src/WPC/Plugin.hs), [GHC late plugins](https://downloads.haskell.org/ghc/9.10.3/docs/users_guide/extending_ghc.html#late-plugins).

A module archive contains binary External STG, a full-Core interface, pretty-printed Core/STG, Cmm, generated assembly, compilation metadata, and available source/foreign stubs. `writeFullCoreInterface` enables `Opt_WriteIfSimplifiedCore`, calls `tidyProgram`, creates a partial/full interface and writes it. This is a genuine machine-readable Core route, not merely parsing a `-ddump-simpl` listing. It is nevertheless a GHC-versioned interface, not a portable, lossless serialization of every in-memory `ModGuts`/`IdInfo` field. [Modpak source](https://github.com/grin-compiler/ghc-whole-program-compiler-project/blob/a99ba59f7286a46aed19e9faba3acc6833b21920/wpc-plugin/src/WPC/Modpak.hs).

GHC's `mkIface_` puts every Core top binding into `mi_extra_decls` when that flag is enabled. Its interface metadata vocabulary includes arity, demand signature, CPR signature, inline pragma, unfolding, no-CAF information, LF information, and tag signature; rules/specializations are separate. Actual preservation depends on the conversion and pipeline stage. A THC importer must inspect/validate the fields present and preserve additional required metadata explicitly rather than assuming “full Core” means every GHC analysis is present. [GHC interface construction](https://github.com/ghc/ghc/blob/3f4d7d38b9661435bdde981451ac50c4335ed090/compiler/GHC/Iface/Make.hs), [interface syntax](https://github.com/ghc/ghc/blob/3f4d7d38b9661435bdde981451ac50c4335ed090/compiler/GHC/Iface/Syntax.hs).

The README's missing-`IdInfo` TODO needs a precise reading. `StgToExtStg` does store pretty-printed `idInfo` in `sbinderInfo`; it does not export a complete structured `IdInfo` that a new optimizer can safely consume. It also keeps representation types and textual type signatures. The README says the missing information causes `gen-exe` to produce `-O0` executables; this must not be misreported as proving that the originally captured STG had no preceding GHC optimizations. [STG conversion](https://github.com/grin-compiler/ghc-whole-program-compiler-project/blob/a99ba59f7286a46aed19e9faba3acc6833b21920/wpc-plugin/src/WPC/StgToExtStg.hs).

A repository-wide search at this pin found no full-Core importer/consumer beyond producing and packaging `module.fullcore-hi`; consuming it in THC is proposed work. The exporter also uses one process-global `IORef GlobalEnv` to transfer current-module state between hooks, so parallel/module-interleaving correctness must be audited before treating it as production capture infrastructure. [Global state](https://github.com/grin-compiler/ghc-whole-program-compiler-project/blob/a99ba59f7286a46aed19e9faba3acc6833b21920/wpc-plugin/src/WPC/GlobalEnv.hs).

**Proposed export contract:** package/unit/module identity; deterministic binder identity; Core and STG schema/compiler versions; source locations; constructor identities/layout; runtime representations; function arity and calling convention; closure update flags and free variables; let-no-escape/join information; structured demand/strictness, CPR, unfolding and occurrence/one-shot facts where justified; all primops, foreign calls and imported symbols; optimization flags, target ABI, and content hashes. Do not treat ephemeral GHC `Unique`s alone as cross-module stable linkage names. Keep correspondence maps when Core tidying and subsequent lowering rename/split binders. Treat metadata as versioned optimization evidence, never as permission to break lazy semantics.

## Whole-program closure and rebuilding libraries

All **reachable target Haskell definitions** must be available as THC-compatible code: application modules, package dependencies, relevant boot libraries, generated modules, and runtime-rooted Haskell support. Every such library therefore must have been rebuilt/exported at least once under the pinned configuration, or supplied as matching cached exports. Users need not rebuild every package on every invocation. Native `.a`/`.so`/`.o` files and ordinary interfaces do not provide the complete Haskell bodies to a JVM backend. `.hi` unfoldings are selected for compilation needs, not a guarantee that every executable body survives.

Separate these categories:

* **Target Haskell packages:** export once, then reuse artifacts keyed by source, GHC, configuration, ABI and exporter schema. Include hidden modules, wired-in packages, actual unit IDs, and instantiated/renamed units; package-name-only identity is insufficient.
* **Host tools:** Cabal/Stack, preprocessing tools, custom Setup programs, compiler plugins and compile-time code may remain native host executables. They do not all belong in the JVM runtime closure.
* **Intrinsic/runtime definitions:** `GHC.Prim` is compiler-provided; WPC itself excludes it from module lookup. Primops and relevant RTS/Cmm functions need THC implementations or explicit bridges, not invented Haskell bodies.
* **Native dependencies:** package `cbits`, system libraries and generated FFI stubs require a separate ABI decision and artifacts; exporting STG does not translate C/Cmm.

WPC's module discovery reads installed package metadata and looks for exported modpaks in package artifact directories or a foundation-pak. **It currently filters away missing modpak files, and its dependency walk has a commented-out missing-module error.** This is unacceptable as THC's success criterion: add a closure audit that rejects unresolved reachable symbols with their import chain, unless each is explicitly registered as a supported intrinsic/foreign binding. Preserve foreign exports and runtime roots even when no ordinary Haskell caller exists. Its hard-coded `Stg.GHC.Symbols` roots retain older `base/GHC.*` names; audit against the 9.10 `ghc-internal/GHC.Internal.*` organization rather than assuming that table is current. [Module discovery/closure](https://github.com/grin-compiler/ghc-whole-program-compiler-project/blob/a99ba59f7286a46aed19e9faba3acc6833b21920/external-stg/lib/Stg/Program.hs), [runtime-root table](https://github.com/grin-compiler/ghc-whole-program-compiler-project/blob/a99ba59f7286a46aed19e9faba3acc6833b21920/external-stg/lib/Stg/GHC/Symbols.hs).

## Boot-library availability: a concrete gap

Foundation-pak supplies a 9.10.3 **source-build recipe**, not evidence of a ready-made current download. The recipe builds GHC with a stated 9.6.6 bootstrap, patches Hadrian and Cabal, builds the exporter with stage2 GHC, and rebuilds a later stage with the plugin. It pins WPC `6c0bced14e805ef8ccdbf6edc153068ab5b55687`, not the newer WPC revision audited above. Those revisions must be reconciled before claiming the foundation artifacts contain the newly observed full-Core export. The reused Hadrian patch produces `.pak.tar.zst`, while current `Stg.Program`'s automatic downloader constructs `.pak.tar.xz` names. [9.10.3 recipe](https://github.com/grin-compiler/foundation-pak/blob/179f75a4739e8eecc8ddbd1ff7e99225a60c2804/build-foundation-pak-for-ghc-9.10.3.sh), [Hadrian patch](https://github.com/grin-compiler/foundation-pak/blob/179f75a4739e8eecc8ddbd1ff7e99225a60c2804/patch/ghc-9.10.1/hadrian/0001-wpc-9.10.1.patch).

The public GitHub releases API returned only the `ghc-9.2.7` release on the research date, with Darwin arm64/x86_64 and Linux x86_64 artifacts. No 9.10.3 release artifact was verified. Do not let an automatic download silently substitute 9.2.7 exports. THC should publish its own reproducible, hashed foundation set after qualification. [Release listing](https://github.com/grin-compiler/foundation-pak/releases), [queried API](https://api.github.com/repos/grin-compiler/foundation-pak/releases).

The baseline library versions include `base-4.20.2.0`, `ghc-prim-0.12.0`, and `template-haskell-2.22.0.0`; implementation modules live in `ghc-internal-9.1003.0`. Pin the actual full package database and integer backend, not just a base version. The initial foundation must include the reachable pieces of `base`, `ghc-internal`, `ghc-prim`, `ghc-bignum` and further selected libraries; do not claim all boot packages are required for every program. [Release library table](https://downloads.haskell.org/ghc/9.10.3/docs/users_guide/9.10.3-notes.html#included-libraries), [library index](https://downloads.haskell.org/ghc/9.10.3/docs/libraries/index.html).

## Manifest and foreign-symbol policy

WPC already records compiler/target/ways, main and application modules, package identities and module lists, import/library directories, libraries, frameworks, linker options and package databases. It captures C objects/sources and foreign declarations. Its fullpak packaging can retain both Core and STG; `--stgbins-only` intentionally discards the richer assets. Its foreign linker builds a native `cbits.so` while excluding the RTS from the package list. None of these facts imply a JVM-compatible foreign boundary. [Application manifest writer](https://github.com/grin-compiler/ghc-whole-program-compiler-project/blob/a99ba59f7286a46aed19e9faba3acc6833b21920/wpc-plugin/src/WPC/GhcStgApp.hs), [fullpak assembly](https://github.com/grin-compiler/ghc-whole-program-compiler-project/blob/a99ba59f7286a46aed19e9faba3acc6833b21920/external-stg/lib/Stg/Fullpak.hs), [foreign linker](https://github.com/grin-compiler/ghc-whole-program-compiler-project/blob/a99ba59f7286a46aed19e9faba3acc6833b21920/external-stg/lib/Stg/Foreign/Linker.hs).

**Proposed THC manifest additions:** portable content-addressed artifact paths; exact compiler/exporter/schema/runtime ABI identities; source/configuration hashes; defined/imported Haskell symbols; explicit root sets; primop requirements; every foreign symbol with convention, signature, safety, ownership/lifetime, callback requirements and implementing library; native architecture/OS/endianness/word size; constructor and closure representation versions; unsupported requirements diagnosed before execution. Audit reader/writer field symmetry: current WPC writes framework metadata that its `Stg.Program` parser does not retain. A captured link command is evidence of dependencies, not a complete executable compatibility contract.

Foreign calls divide into ordinary C ABI calls, C helpers that understand GHC layouts, GHC RTS APIs, and `foreign import prim` calls into Cmm using GHC's internal calling convention. Only the first category is a plausible straightforward native bridge. A Java object cannot be passed as a GHC heap closure. `ByteArray#` address stability, `Addr#`, pinned storage, `StablePtr#`, function wrappers, foreign exports, finalizers, safe callbacks, interruptibility and bound-thread behavior all need deliberate contracts. GHC guarantees particular behavior even for `unsafe` FFI (including calling-thread/no-GC behavior); an arbitrary JNI call is not automatically equivalent. [GHC FFI contracts](https://downloads.haskell.org/ghc/9.10.3/docs/users_guide/exts/ffi.html).

Prefer an explicit initial supported-FFI subset plus early rejection over dummy RTS symbols. A `cbits.so` loading successfully proves neither semantic compatibility nor correctness of callbacks. Bridge isolated byte buffers and scalar C ABI calls first. Packages dependent on heap introspection, compact regions, GHC stack layout, dynamic Haskell object linking, or internal RTS state need dedicated support or an explicit limitation.

## Ordinary Haskell versus intrinsic/runtime semantics

Lists, dictionaries, most library algorithms, normal exception values, and much of `IO`'s Haskell scaffolding should remain exported ordinary Haskell. The runtime must supply the operations that make those definitions meaningful: call-by-need closures, thunk update/blackholing, sharing, application/PAP/oversaturation, constructor inspection, primitive values and multi-value returns, mutable state, exceptions and masking, threads/MVars/STM, weak pointers/stable identity, and supported foreign interaction. Not every runtime operation must be implemented on day one, but every program's reachable requirements must be checked.

`IO`'s `State# RealWorld` token is an IR sequencing discipline, not a request to materialize an operating-system object for every token. Erasing representation-free tokens is legitimate only while preserving the ordering/control dependencies GHC established. Primitive operations are not all foreign calls, and foreign calls are not all primops. `Integer`/`Natural` implementation decisions likewise involve both Haskell representation and selected primitive/native backend; replacing them wholesale with Java `BigInteger` requires an intentional representation boundary and consistent handling of exposed constructors and low-level operations.

This approach executes ordinary GHC-compiled programs with ordinary Haskell nontermination and exceptions. There is no normalization fallback, no neutral-term evaluator, and no `NeutralException` control path in the proposed contract. A missing runtime operation is a compile/link-time unsupported-feature diagnostic, not a neutral value propagated at runtime.

## Template Haskell, plugins and two execution worlds

Recommended first route: retain native GHC compilation for compile-time execution and artifact production. Template Haskell splices, annotations, preprocessors and plugins execute in the host world; generated code then passes through the exporter and runs in THC. Keep host compile-time dependencies separate from target runtime dependencies. For packages shared by both worlds, both artifacts may be needed. Host execution must use matching versions/configuration; target-specific CPP, `hsc2hs`, header constants, pointer sizes and foreign assumptions cannot be borrowed blindly from whichever host compiled the package.

A later true cross-target compiler is a separate integration project. GHC's external interpreter is a protocol/process mechanism; it does not make arbitrary JVM Haskell closures ABI-compatible with GHC's interpreter. Its remote interpreter requires target-side execution support, and file/process IO occurs in that execution environment. GHC documents `-fplugin-library` as a cross-compiler workaround while also documenting restrictions on ordinary plugins with `-fexternal-interpreter`; pin and test the exact combination rather than asserting all plugins work. [Plugin loading](https://downloads.haskell.org/ghc/9.10.3/docs/users_guide/extending_ghc.html#using-compiler-plugins), [remote interpreter](https://downloads.haskell.org/ghc/9.10.3/docs/users_guide/ghci.html#running-the-interpreter-on-a-different-host).

## Eta: useful evidence with a strict boundary

Eta calls itself a Haskell dialect and explicitly targets compatibility with GHC **7.10.3**. The inspected README reports Eta **0.8.6b5**. Its source contains a forked compiler, customized libraries, Java FFI, integer integration and a substantial Java runtime with thunks, PAPs, scheduler/concurrency machinery and exceptions. This demonstrates the scale and feasibility of a JVM Haskell runtime. It does not provide a modern GHC 9.10 adapter or a drop-in Truffle implementation. [Pinned README](https://github.com/typelead/eta/blob/97ee2251bbc52294efbf60fa4342ce6f52c0d25c/README.md), [runtime](https://github.com/typelead/eta/tree/97ee2251bbc52294efbf60fa4342ce6f52c0d25c/rts/src/main/java/eta/runtime), [libraries](https://github.com/typelead/eta/tree/97ee2251bbc52294efbf60fa4342ce6f52c0d25c/libraries).

Study Eta's application/update/exception contracts and library-porting decisions; do not inherit its old GHC frontend as THC's language definition. Any reuse requires a semantic and license audit. The preferred architecture keeps a current pinned GHC frontend and a small explicit adapter, with THC owning its runtime contract.

## Acceptance gates before implementation claims

1. Reproducibly build a 9.10.3 exporter and matching foundation exports from pinned sources; verify full-Core and STG presence for each required module.
2. Run a closure audit over a real Cabal-built program with library dependencies; make deliberately missing modules/primops/foreign symbols fail clearly.
3. Decode full-Core interfaces with the matching GHC and validate metadata/correspondence against emitted STG; do not base optimization on parsed pretty-print strings.
4. Start execution with genuine GHC STG for pure lazy examples and selected base functionality; compare results, forcing behavior, exceptions and sharing to native GHC.
5. Qualify library/primop/FFI capabilities incrementally and publish an exact compatibility matrix. TH/plugins, callbacks, asynchronous exceptions and concurrency need their own tests before broad claims.

The architecture is credible; broad library compatibility and performance remain hypotheses requiring these gates.
